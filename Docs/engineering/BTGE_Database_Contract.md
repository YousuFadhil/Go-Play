> of them, this document is the defect.**

## 1. Purpose

This contract exists because **BTGE is the only component in the product that
reads across four tables, computes over them, and produces a record that every
downstream figure depends on** — and because it is a *producer that owns
nothing it touches*.

That combination is unusual enough to need a written boundary:

- It reads the roster, the profiles, the match and the community's recent
  lineups.
- It produces the lineup, which defines participation, which defines results,
  which define statistics and ratings, which define leaderboards.
- **And it owns none of them.** Not the roster it reads, not the lineup it
  proposes, not a single figure downstream.

Without a frozen contract, the natural drift is for a producer with that reach
to acquire ownership one column at a time — a stored quality metric here, a
"generated by engine" flag there — and each step would be individually
defensible and collectively fatal to `KB-007` and `KB-014`.

**So the purpose is negative as much as positive: to state what BTGE may do,
and to make everything else refusable by reference.**

## 3. Responsibilities

### 3.1 What BTGE owns

| # | Owned | Meaning |
|---|---|---|
| 1 | **The proposal** | Given a valid input set, which players go on which side, in which positions, on what basis |
| 2 | **The positioning chain** | Which of `PRIMARY`, `SECONDARY` or `TRANSITION` produced each position |
| 3 | **Quality metrics** | Computed and returned with every result — and **stored nowhere** (§6.2) |
| 4 | **Determinism of its own output** | The same inputs produce the same result. There is no seed |
| 5 | **Refusing an invalid request** | A missing Core Player Input is a caller error; the engine rejects rather than substituting |

### 3.2 What BTGE does **not** own

| # | Not owned | Owner | The rule that says so |
|---|---|---|---|
| 1 | **The lineup** | The **organiser** | `BTGE-MO-3`: the engine does not re-optimise, revert or block a manual change; the organiser's decision stands **including when it worsens every metric** |
| 2 | **Whether a proposal is stored** | The organiser | Generation writes nothing (§5.1). Storing is a separate, deliberate act |
| 3 | **Eligibility** | `match_registrations` | The engine receives a set; it does not decide who is in it |
| 4 | **Any player attribute** | `users` | It reads four Core Player Inputs and writes none of them — including the rating |
| 5 | **Capacity, timing, or the match** | `matches` | It reads the match date and nothing else |
| 6 | **Every downstream figure** | The results and statistics tables | §6.2 |
| 7 | **Its own history** | Nothing | `BTGE-AX-5`: nothing about an override is retained; and nothing about a *generation* is either (§9.3) |

### 3.3 The producer/owner distinction, stated once

> **BTGE proposes; the organiser disposes; the database records what the
> organiser chose.**

Three approved rules make this binding rather than stylistic: `BTGE-MO-3` (the
decision stands), `BTGE-MO-6` (metrics never used to warn against or undo a
change), and `KB-007` (no feedback loops). Together they mean **the engine has
no standing to object to the contents of the table it feeds** — which is why
that table stores nothing the engine would need in order to object.

## 4. Database Input Contract

BTGE consumes **three reads**. No other database access is part of the
contract, and any future read is a change to it.

### 4.1 Input 1 — the eligible roster and its player inputs

| Property | Value |
|---|---|
| **Source table** | `match_registrations`, joined to `users` |
| **Selection** | Registrations of **one match** whose status is **`confirmed`** |
| **Ordering** | **Deterministic, and required to be** — §4.5 |
| **Required fields — from `users`** | `id`, `overall_rating`, `date_of_birth`, `primary_position`, `secondary_position` |
| **Ownership** | `match_registrations` owns *who is eligible*; `users` owns *every attribute*. BTGE owns neither |
| **Validation expectation** | **The caller validates; the engine refuses.** §4.4 |

**Four of the five fields are the Core Player Inputs** (`KB-006`, engine
specification §4.1). The fifth, `id`, is identity.

**Only `confirmed` registrations are eligible.** Reserves are not in the
generation set: a reserve holds a place in the queue and nothing else, and
`BTGE-HC-3` forbids the engine reducing a set it was given — so handing it
reserves would force it to assign them.

**Any additional column read alongside is presentational and must not reach the
engine.** The display name travels with the roster for the organiser's screen;
`KB-006` fixes the Core Player Inputs at four, and a fifth evaluated attribute
would breach it whether or not it was intended as one.

### 4.2 Input 2 — the match date

| Property | Value |
|---|---|
| **Source table** | `matches` |
| **Required field** | `start_at` |
| **Ownership** | `matches` |
| **Purpose** | Age is computed as completed years between date of birth and the match date. It is **derived at generation time and never stored** |
| **Validation expectation** | `start_at` is NOT NULL by constraint; no further check is required |

**It is a contextual input, not a player attribute** (engine specification
§4.2). It is listed in the contract because omitting it would make age
uncomputable, not because it describes anyone.

**One property of this input is device-dependent**, and the contract records it
rather than correcting it: the match date is read in the device's local time,
consistent with `DD-11`. §14.2 states what that means for reproducibility.

### 4.3 Input 3 — Match History (auxiliary data)

| Property | Value |
|---|---|
| **Source table** | `match_team_assignments`, reached through `matches` |
| **Selection** | Lineups of matches in **the same community**, excluding the match being generated, whose end has passed, that **have a stored lineup**, most recent first, bounded by the lookback window |
| **Required fields** | `user_id`, `team` — and, from the match, its start time for ordering |
| **Bound** | `OP-6`, **resolved: the last 5 matches** |
| **Ownership** | `match_team_assignments` — it *is* Match History |
| **Validation expectation** | **None. Absence is never an error** |

**This input is categorically different from the other two**, and the
difference is a rule rather than a nuance:

| `BTGE-AX-n` | Constraint on this input |
|---|---|
| `BTGE-AX-1` | May be consulted **only** during Diversity optimisation — priority 5 — and only after priorities 1–4 are already satisfied |
| `BTGE-AX-2` | Must **never** affect rating, position assignment, age balancing, team strength, or any priority above Diversity |
| `BTGE-AX-3` | Is **only a deterministic tie-breaker** between equivalent solutions. It selects among equals; it never ranks |
| `BTGE-AX-4` | Deriving a rating, strength estimate, position preference or chemistry model from it is **forbidden** — that is behavioural inference, excluded by `KB-014` |
| `BTGE-AX-5` | Where a match was manually adjusted, the lineup that **actually played** is what Match History contains (`KB-017`) |

**The absence path is approved, not exceptional.** `BTGE-DV-5`: with no
history — a new community, a first match, players who have never played
together — Diversity contributes nothing and any remaining tie is broken by the
engine's canonical ordering. **The contract therefore permits this read to
return nothing, and permits it not to be performed at all** when the window is
unset.

### 4.4 The validation boundary — who checks what

**The database records what it knows; the caller validates completeness; the
engine refuses an incomplete request.** Three layers, three different jobs, and
conflating them is what §4.3 of the engine specification forbids.

| Layer | Responsibility |
|---|---|
| **Database** | Guarantees types, vocabularies and ranges: position values, the rating's `0.0 … 10.0` bound, `NOT NULL` where a fact must exist. **It does not guarantee completeness** — `date_of_birth` is deliberately nullable, because accounts predating the requirement have none and inventing one is forbidden |
| **Caller (the assembling layer)** | Reads the roster and **refuses to build an input set** if any confirmed player lacks a required input. This is where the missing-date check lives |
| **Engine** | **Rejects the request rather than substituting a default.** It must never invent a rating, a date of birth, or a primary position |

**The contract term:** *a valid input set contains, for every player, all four
Core Player Inputs with `secondary_position` optionally absent.* Anything less
is a caller error, and neither the database nor the engine repairs it.

### 4.5 Determinism of the input sequence — a contract term

`BTGE-PF-7` requires every remaining tie to be broken by **deterministic
canonical ordering**, *"never from unordered iteration, hash ordering, thread
scheduling, or wall-clock time."*

**A deterministic engine over a non-deterministically ordered input is not
deterministic.** So the contract requires:

> **Every read in §4.1 and §4.3 must impose an explicit, stable ordering.**

The roster read satisfies this today by ordering on registration order, and the
history read by ordering on match start time descending.

**But this creates a second obligation, and it is the sharper one:**

> **The engine's canonical ordering must not be the input sequence.**

Registration order is *arrival order* — behavioural data. If the canonical
tie-break inherited the input sequence, then who registered first would
influence which of two equally optimal lineups is chosen, and that is
behavioural inference by the back door (`KB-014`, `BTGE-AX-4`).

**Stated as a contract term:** the tie-break must be computed from a stable
property of the players themselves — their identity — and never from the order
in which the database returned them. **Recorded as `BDC-R1` for verification
against the engine**, not as a confirmed defect: this contract does not read the
algorithm.

## 5. Database Output Contract

**BTGE produces exactly one output, and it is not a write.**

### 5.1 The proposal is returned, not stored

**Generation writes nothing.** The engine returns a proposed lineup and its
quality metrics to the caller, and the caller renders it. **Storing is a
separate, deliberate act performed by the organiser** — which is what makes
`BTGE-MO-2` possible at all: the organiser may move a player *before the lineup
is settled*, and `KB-017` records what actually played rather than what was
proposed.

**This is the single most important term in the output contract.** A generation
that stored its own result would make the engine the author of the record, and
every rule in §3.2 would become unenforceable.

### 5.2 The stored output, when the organiser stores it

| Property | Value |
|---|---|
| **Destination table** | `match_team_assignments` |
| **Shape** | One row per player: the match, the player, the team, the assigned position, the assignment basis |
| **Ownership** | **The organiser** (`BTGE-MO-5`). The engine authored the values; it owns neither the decision to store them nor the record afterwards |
| **Write mode** | **Whole-lineup replacement, in one transaction** — §7 |
| **Authorisation** | Owner or admin of the match's community |

### 5.3 Required guarantees of a stored proposal

A proposal the engine returns must satisfy every hard constraint before it is
storable. **The contract states which guarantees the engine owes and which the
database independently enforces**, because the two lists are not the same and
the difference is where §16's findings live.

| Guarantee | Owed by the engine | Independently enforced by the database |
|---|---|---|
| Every player assigned to exactly one team (`BTGE-HC-1`) | **Yes** | **Partly** — *at most* one is enforced; *at least* one is not |
| No player appears twice (`BTGE-HC-2`) | **Yes** | **Yes** |
| No player dropped (`BTGE-HC-3`) | **Yes** | **No** |
| Team sizes balanced (`BTGE-HC-4`) | **Yes** — in generation | **No, and correctly not**: `BTGE-MO-4` omits it, because moving one player necessarily unbalances the sides |
| Positions from the four (`BTGE-HC-5`) | **Yes** | **Yes** |
| No team with two goalkeepers (`BTGE-HC-6`) | **Yes** | **Yes** |
| A valid solution for any valid input (`BTGE-HC-7`) | **Yes** | n/a — an engine property |

**The contract term that follows:** *the database enforces the guarantees that
must hold for any lineup however it was produced; the engine owes the rest.* A
second engine (§13.1) inherits the same division — it must own `HC-1`, `HC-3`
and `HC-4` itself, because nothing below will catch it.

### 5.4 Generation metadata — none, and none may be added

**No metadata about the generation is stored. Not the metrics, not the
parameters, not the engine version, not a "generated" marker, not a timestamp
of the run.**

| Candidate | Why it is refused |
|---|---|
| Quality metrics | `BTGE-MO-6`: metrics may be recomputed and **never** used to warn against, discourage or undo the organiser's change. A stored metric is one query away from being a rule |
| A "generated vs adjusted" marker | `KB-017` and `BTGE-AX-5`: nothing about the override is retained. A stored provenance flag is one query away from being an input, which `KB-007` and `KB-014` forbid |
| Engine version or parameters | Would make the record self-describing in a way that invites reproducing an old result — but `BTGE-MO-5` makes the *stored* lineup authoritative, not the run that produced it |
| A generation timestamp | The stored lineup carries when it was stored. When it was *computed* is not a fact about the match |

**The general rule:** *the record holds what played, never how it was reached.*

## 6. Write Boundaries

### 6.1 What may be written on BTGE's behalf

**Exactly one table, through exactly one operation: `match_team_assignments`,
by whole-lineup replacement.**

There is no other write in the contract. Not a flag on the match, not a
counter, not a log.

### 6.2 What BTGE must **never** write

Each row states the rule and why it is not merely undesirable but breaks
something specific.

| Must never write | Why |
|---|---|
| **`match_results`, `match_goals`** | Results are recorded by an organiser after the match, over the final lineup. An engine that could write one would be asserting an outcome it has no knowledge of |
| **`player_statistics`, and any future Level 2 statistics** | Statistics arise **only from a recorded result** (`A4`). A statistic written by the engine would be a figure with no result behind it, unreversible by the correction path |
| **`rating_history`, and `users.overall_rating`** | **The rating is a Core Player Input.** An engine that could write the input it reads is a feedback loop — precisely what `KB-007` forbids — and `RR-2` already made the rating system-managed with the rating engine as sole author. **This is the most important prohibition in the contract** |
| **`match_registrations`** | Eligibility is decided by the roster and the queue. An engine that could add a registration could enlarge its own generation set; one that could remove a registration could drop a player, which `BTGE-HC-3` forbids |
| **`matches`** | The match's capacity, timing and status are the organiser's and the system's. In particular the engine must not mark that generation has run — no such column exists, and §5.4 is why |
| **`communities`, `community_members`, `community_invitations`** | Community data is outside the Match aggregate entirely. Authority comes from `community_members.role` and nowhere else; an engine that could write it could authorise itself |
| **`users` — any column** | Four inputs are read; none is written. A profile is the player's, except the rating, which is the rating engine's |
| **`notifications`** | The engine has nobody to notify. Notification is the organiser's operation's business |

### 6.3 The boundary stated as one rule

> **BTGE reads five tables' worth of facts and contributes one table's worth of
> proposal. Everything it reads is owned by someone else, and the one thing it
> produces is owned by the organiser the moment it is stored.**

## 7. Transaction Contract

### 7.1 Atomicity

| Operation | Atomicity requirement |
|---|---|
| **Generation** | **None.** It is a pure computation with no database write. It cannot leave the database in any state |
| **Storing a lineup** | **All or nothing.** The replacement — clearing the previous lineup and writing the new one — must be a single transaction |

**Why the second is a requirement and not a preference.** Performed as two
statements, a failure between them leaves the match with **no lineup at all**,
having destroyed a good one and reported nothing wrong. Generation could
survive that — it writes a lineup that did not exist a moment earlier — but
**manual adjustment cannot**: every adjustment rewrites the whole lineup, so
the same window sits under a routine edit of a lineup that matters.

### 7.2 Failure and rollback

| Failure | Behaviour |
|---|---|
| A required input is missing | The **caller refuses to assemble the input set**. Nothing is read further, nothing is computed, nothing is written |
| The engine cannot produce a valid solution | **Not a permitted outcome** for a valid input in the supported range (`BTGE-HC-7`). Returning "no solution" is not allowed |
| The store is unauthorised | Refused before anything is deleted |
| The store breaches a database constraint | **The whole replacement rolls back.** The previous lineup remains exactly as it was |
| The store fails midway | Impossible by §7.1 — there is no midway |

**The contract term:** *a refused store leaves the previous lineup untouched.*
An organiser who attempts an invalid change ends where they began, not with
nothing.

### 7.3 Match locking

**The Match Row Lock Principle applies to every write in the Match aggregate**
(§10.2). The store is a write in that aggregate.

**A note the contract must be honest about:** the lineup store today authorises
and replaces, and **does not itself take the match row lock** that every roster
operation takes. Two consequences:

- **It does not currently race anything**, because no other operation writes
  `match_team_assignments`, and the replacement is internally atomic.
- **It is not protected against a future one.** A second writer of this table —
  a draft mode operation, a captain-pick operation, a server-side regeneration
  — would race it, and the discipline that would have prevented that is absent
  here while present everywhere else in the aggregate.

**Contract term:** *any operation writing `match_team_assignments` takes the
match row lock first.* Recorded as `BDC-R2`, §19 item 2.

### 7.4 Concurrency expectations

| Scenario | Expectation |
|---|---|
| Two organisers generate simultaneously | **Permitted and harmless.** Generation is pure; neither writes |
| Two organisers store simultaneously | **Last write wins, and each is internally consistent.** Neither can produce a half-lineup. Under `BDC-R2` they would serialise |
| An organiser stores while another adjusts | Same. The adjuster reads the stored lineup first, so a refused edit leaves the previous lineup as it was |
| A registration changes during generation | **The proposal becomes stale.** Nothing detects it — §16.4 |
| A lineup is stored after a result was recorded | **Permitted, and it is the live known limitation** — §9.4 |

## 8. Manual Override Contract

### 8.1 What happens after a manual adjustment

**The adjusted lineup becomes the authoritative lineup for that match**
(`BTGE-MO-5`). It is what is recorded, what feeds Match History, what defines
participation, and what every downstream figure is computed from.

**Nothing else happens.** The engine is not rerun, no metric is recomputed for
storage, no warning is produced and nothing is compensated. `BTGE-MO-3` is
explicit: *the organiser's decision stands, including when it worsens every
quality metric.*

### 8.2 What an override may change

| Permitted | `BTGE-MO-2` |
|---|---|
| Move a player between teams | ✔ |
| Swap two players | ✔ |
| **Without rerunning the engine** | ✔ — this is the stated point |

| Not permitted by `BTGE-MO-2`, and therefore not part of this contract |
|---|
| Adding a player who was not in the generation set |
| Dropping a player (`BTGE-HC-3`, `BTGE-MO-4`) |
| Leaving a player unassigned (`BTGE-MO-4`) |
| Changing a position — §13.2 records what a future one would need to settle |

**Which hard constraints survive an override** (`BTGE-MO-4`): no duplication,
no dropping, nobody unassigned, no team with two goalkeepers. **Team size
balance does not**, and that is deliberate — moving one player necessarily
unbalances the sides.

### 8.3 What BTGE may regenerate

**Everything, and it is a full replacement.** Regeneration is not a repair or a
merge: it discards the stored lineup entirely and proposes a new one from the
current roster.

**Two terms:**

- **Regeneration must be an explicit act.** The engine must never regenerate as
  a side effect of anything — not of a registration change, not of an override,
  not of a read. `BTGE-MO-3` forbids the engine reverting a manual change, and
  a silent regeneration is the most complete revert available.
- **A regenerated proposal is a proposal.** It is stored only if the organiser
  stores it (§5.1).

### 8.4 What BTGE must preserve

| Must preserve | Why |
|---|---|
| **The stored lineup, until explicitly replaced** | `BTGE-MO-5` |
| **The organiser's change, in full** | `BTGE-MO-3` |
| **Its own ignorance of the override** | `BTGE-AX-5`: nothing about the override is retained. The engine must not know a lineup was adjusted, must not treat an adjusted lineup differently in Match History, and must not learn from it (`KB-007`, `KB-014`) |
| **The read-then-write discipline for adjustments** | An adjustment reads the stored lineup before changing it, because the organiser's screen may be older than the record and `BTGE-MO-5` makes the record authoritative |

### 8.5 The override paradox, resolved

There is an apparent contradiction worth stating and dissolving, because a
reader will find it:

> *If manual overrides must not train the engine (`KB-007`, `KB-014`), how can
> an adjusted lineup enter Match History, which the engine consults?*

**`KB-017` resolves it, and the resolution is the boundary this contract
depends on:** what enters history is **the lineup that actually played** — a
fact about reality. What is forbidden is retaining anything about *the override
itself*: that it happened, who made it, what it changed, or any pattern across
overrides. **The engine sees a lineup; it never sees that the lineup was
edited.**

## 9. Historical Contract

### 9.1 Why historical assignments are immutable in practice

**They are not immutable by constraint** — nothing stops a stored lineup being
replaced — and the contract must not claim otherwise. What makes them
historical is that, after the match, **nothing has a reason to change them**:
the match is completed, the result has been recorded from them, and every
figure downstream was computed over them.

**The contract term is therefore a discipline, not a guarantee:**

> **A lineup for a completed match is a historical record. No operation may
> rewrite it, and BTGE must never regenerate over it.**

§9.4 states what happens when that discipline is broken, because it currently
can be.

### 9.2 Why BTGE never rewrites history

Three independent reasons:

1. **It has no reason to.** The engine's product is a proposal for a match that
   has not been played. A completed match has no proposal to make.
2. **`BTGE-AX-4` depends on history being factual.** Match History is *the
   factual record of who played together*. An engine that could rewrite it
   could rewrite its own auxiliary input — a feedback loop by a longer route.
3. **`BTGE-MO-5` gives the stored lineup authority the engine cannot override.**
   The organiser's lineup is authoritative; regenerating over it would be the
   engine asserting otherwise.

### 9.3 The engine keeps no history of its own

**There is no record of any generation run.** Not the metrics, not the
parameters, not when it ran, not how many times.

This is deliberate and follows from §5.4: a record of runs is a record of what
the organiser rejected, and a record of what the organiser rejected is exactly
the override-pattern data `KB-007` forbids acting on and `BTGE-AX-5` forbids
retaining.

**Consequence, stated plainly:** the product cannot answer *"was this lineup
generated or hand-picked?"* or *"how many times did the organiser regenerate?"*
Both are deliberate blindnesses, not gaps.

### 9.4 Relationship with Results

**Results depend on the final assignments, absolutely.** A result cannot be
recorded without a stored lineup; the scorer and MVP checks resolve against it;
and every counter is computed from it.

**The live limitation, restated because this is the contract that should carry
it:** nothing prevents a lineup being replaced *after* its result is recorded.
If it is, and the result is then corrected, the reversal computes over the
**new** lineup and subtracts something other than what was added.

**This is `RR-7`'s recorded limitation.** It is known, documented and **not
approved for work** — guarding it means refusing a lineup edit once a result
exists, which is a new refusal outside the approved scope. **The contract
records it as inherited, and does not resolve it** (`BDC-R3`).

### 9.5 Relationship with Ratings

**Ratings are immune to a lineup changing, and this is worth understanding
rather than assuming.**

A rating reverses from `rating_history` — an append-only record of the *applied*
delta, entry by entry — not by recomputing over the lineup. So even if a lineup
is replaced after a result was recorded, the rating reversal remains exact.

**The counters are not immune**, because they *are* recomputed over the lineup.
So a lineup edit after a recorded result corrupts statistics and leaves ratings
correct — an asymmetry that follows directly from one being an audit and the
other a cache.

**The contract term:** *BTGE never causes a rating change, directly or
indirectly, at generation time.* A rating moves only when a result is recorded.
Storing a lineup moves nothing.

## 10. Engineering Principles

The brief names six approved principles. **Two have no textual definition
anywhere in this repository, and two more have no named definition though their
substance is documented.** Rather than assume, this section states the reading
applied and marks its basis — consistent with the caveat this phase has
recorded eight times about the absent *Database Principles* document.

| Principle | Basis in the repository | Reading applied |
|---|---|---|
| Match Aggregate Root | **Documented** — `06-ERD.md` §1, `Matches_Table_Specification.md` §5 | As documented |
| Match Row Lock Principle | **Evidenced, not named** — the discipline appears in every roster operation, with the comment *"same lock order as every other roster write: match row first"* | As evidenced |
| Business Transition Principle | **No definition found** | §10.3 — stated reading |
| Historical Identity Principle | **Substance documented** — `KB-017`, approved context item 10 | §10.4 — stated reading |

**If any reading below differs from the approved definition, this document is
the defect** and should be corrected against it.

### 10.1 Match Aggregate Root

**Reading:** everything about a game hangs beneath the match, and every
operation in the domain takes a match id and resolves authority through the
match's community.

**How it constrains BTGE:**

- Generation is **per match** and cannot span two. There is no cross-match
  optimisation, and a future one would be a new aggregate, not a new parameter.
- Authorisation for storing a lineup comes from the **match's community role**,
  never from the engine and never from who created the match.
- **The single exception is Match History**, which reads *across* matches — and
  it is bounded twice: to one community, and to the `OP-6` window. That
  boundedness is what keeps a cross-match read from becoming a cross-match
  aggregate.

### 10.2 Match Row Lock Principle

**Reading:** every write in the Match aggregate takes an exclusive lock on the
match row first, in that order.

**How it constrains BTGE:**

- **Generation is exempt because it writes nothing.** A pure read need not lock,
  and locking for it would serialise an operation with no side effects.
- **Storing is not exempt** — and §7.3 records that today it does not take the
  lock, which is `BDC-R2`.
- **The order is match-first, always.** A future server-side generation that
  locked profiles before the match would deadlock against registration.

### 10.3 Business Transition Principle

**Reading applied:** *a state change in the domain happens only through the
business operation that owns it — never through a direct write that reaches the
same state by another route.*

**How it constrains BTGE:**

- A lineup enters existence **only** through the storing operation. There is no
  second route, and the direct write path that still exists on the table is a
  breach of this principle rather than an alternative (§16.2).
- **Generation is not a transition.** It changes nothing, so it is not subject
  to the principle — which is exactly why it needs no authorisation, no lock and
  no transaction.
- A future engine cannot introduce its own write path; it must produce a
  proposal and hand it to the same operation.

### 10.4 Historical Identity Principle

**Reading applied:** *a historical record states what happened, identified by
the entities that took part — never by the process that produced it, and never
by references that can be recreated.*

**How it constrains BTGE:**

- The lineup records **players, teams and positions** — not the engine, not its
  version, not its metrics (§5.4).
- **Nothing may reference an assignment row**, because every store replaces
  every row. History is identified by *(match, player)*, which survives.
- `KB-017` is this principle applied: the adjusted lineup is history **because
  it is what happened**, and the adjustment is not history because it is process.

### 10.5 Final Participation Principle

**Reading applied:** *participation in a match is defined by exactly one record
— the final assignments — and every downstream consumer resolves participation
there and nowhere else.*

**How it constrains BTGE:**

- The engine **consumes eligibility** (`match_registrations`) and **produces a
  proposal for participation**. It does not define participation: storing does.
- Results, goals, MVP, ratings, statistics and Match History all resolve
  participation against the lineup — **so anything the engine proposes and the
  organiser stores becomes a participant**, with every consequence that carries.
- **This principle is what makes §16.1 serious**: an unconstrained lineup is an
  unconstrained definition of participation.

### 10.6 Single Business Path Principle

**Reading applied:** *one business outcome has one code path. Where two callers
need the same outcome, they delegate to one body rather than each implementing
it.*

**How it constrains BTGE:**

- **Generation, manual adjustment and clearing are one write path**, not three.
  They differ only in what they hand it.
- A second engine must reuse that path, not add one (§13.1).
- The corollary is the strongest argument for closing §16.1: **because there is
  one path, one validation closes the gap for every producer** — the current
  engine, a future one, draft mode and captain picks alike.

## 11. Dependencies

### 11.1 Tables BTGE depends on

| Table | Direction | Purpose | What BTGE may do |
|---|---|---|---|
| `match_registrations` | Read | The generation set — confirmed only | **Read only.** Never write |
| `users` | Read | Four Core Player Inputs | **Read only.** Never write, and never the rating above all |
| `matches` | Read | `start_at`, for age; `community_id`, for authorisation | **Read only** |
| `match_team_assignments` | Read **and** write | Match History (read); the stored lineup (write, via the operation) | The **only** table written on BTGE's behalf |
| `community_members` | Indirect | Resolves whether the caller may store | Never read directly by the engine; consulted by the operation's authorisation |

### 11.2 Tables depending on BTGE's output

**None by foreign key. All of them by behaviour** — and this is the asymmetry
that makes the contract necessary:

| Consumer | Dependency |
|---|---|
| `match_results` | Cannot exist without a stored lineup; its MVP must be a participant |
| `match_goals` | Every scorer must be a participant |
| `rating_history` | Every entry is produced by arithmetic over the lineup |
| `player_statistics` | Every counter is applied and reversed over the lineup |
| Level 2 statistics and the Community Rating *(unbuilt)* | Will apply and reverse the same way |
| Leaderboards *(unbuilt)* | Read Level 2 records, which are computed from results, which are computed from the lineup |
| **BTGE itself** | Match History is its own past output — the **only loop in the system**, and it is bounded by `BTGE-AX-1`…`AX-5` |

**That last row deserves emphasis.** BTGE reads its own past output. The five
`BTGE-AX-n` rules exist precisely to keep that loop from becoming a feedback
loop: bounded to priority 5, only as a tie-breaker, never as a ranking, never
inferred from.

### 11.3 Operations BTGE depends on

| Operation | Role |
|---|---|
| **The lineup replacement** | The only write. Authorises, clears and rewrites in one transaction |
| **The community-admin predicate for a match** | Resolves authority from the match's community. Used by the operation, not by the engine |

**No other operation is part of the contract.** In particular BTGE depends on
**no** result, statistics or rating operation — the dependency runs entirely the
other way.

## 12. Future Compatibility

### 12.1 Alternative balancing engines

**Fully supported, with no database change.**

The contract is expressed in inputs and outputs, not in an algorithm. A
replacement engine satisfies it by consuming §4 and producing §5.

**Three obligations it inherits**, and they are the reason §5.3 lists the split
explicitly:

1. **It owns `BTGE-HC-1`, `HC-3` and `HC-4` itself.** The database does not
   enforce them, so a second engine that assumed it would would silently
   produce invalid lineups.
2. **It writes nothing.** It returns a proposal; the same operation stores it
   (§10.6).
3. **It inherits the auxiliary-data bounds** if it consults Match History at
   all — or it may ignore history entirely, which `BTGE-DV-5` already treats as
   an approved path.

### 12.2 Draft mode

**Supported as a producer, with no database change.**

A draft is an organiser assembling a lineup by hand. It produces the same rows
through the same operation, and the database cannot tell the difference —
`KB-017` means it does not need to.

**One question it must settle, and it is not a schema question:** what
`assignment_basis` a hand-picked position carries. Adding a fourth value would
silently reduce the out-of-position count, which the engine specification
defines as **exactly** `TRANSITION`. **Deriving the basis from the player's
declared positions using the same transition chain preserves that definition**
and is the recommendation.

### 12.3 Captain picks

**Supported as a producer, with at most one additive column.**

Captains picking alternately is a process; the lineup it produces is the same
shape. If a captain must be recorded, it is a nullable attribute of an
assignment — additive, and outside this contract.

**The rule not to break:** *a captain is not a role and grants nothing.*
Authority comes from the community role and nowhere else, and a captain
attribute that started gating operations would be a second authorisation
source.

### 12.4 AI-assisted balancing

**Supported as a producer — and this is the case the contract's negative terms
were written for.**

An AI proposer is, contractually, indistinguishable from BTGE: it consumes §4,
produces §5, and stores nothing itself.

**Three prohibitions apply with particular force, and none is new:**

| Prohibition | Why it matters more here |
|---|---|
| **It may not write `users.overall_rating`** (§6.2) | A model that could adjust the rating it reads is the feedback loop `KB-007` forbids, closed in one step |
| **It may not retain override patterns** (`BTGE-AX-5`, `KB-014`) | "Learning from what organisers changed" is the single most natural feature to build on this data and is explicitly forbidden. **This is behavioural inference, and no framing makes it otherwise** |
| **It may not store metrics or confidence** (§5.4) | `BTGE-MO-6`: a stored score is one query from being used to discourage a change |

**The contract needs no amendment to admit such an engine, and admits it under
exactly the same terms.** That is the test of whether the boundary was drawn in
the right place.

### 12.5 Multiple balancing strategies

**Supported, and the database is already indifferent.**

Several strategies — balanced, random, by position, by rating — are several
producers behind one storing operation. The stored record is identical in every
case, because it records *what played*, not *how it was chosen* (§5.4).

**The one thing that would need care:** if a strategy is a persistent community
*setting* rather than a per-generation choice, that setting belongs on the
community, not here, and it is a Product Decision. **No strategy identifier may
be stored on the lineup** — that is generation metadata, which §5.4 refuses.

### 12.6 Where the engine executes

**The contract is agnostic**, under two conditions:

1. **The write remains one operation**, wherever it is invoked from.
2. **A server-side engine takes the match row lock** before storing, which the
   client path currently does not (`BDC-R2`).

## 13. Engineering Review

**Six findings.**

### 13.1 Ownership violation — the lineup's contents are unconstrained

**Nothing validates that a stored lineup contains exactly the match's confirmed
registrants.** The store accepts a client-supplied set of player ids.

**In contract terms this is a breach of the Final Participation Principle
(§10.5):** participation is defined by this record, and the record's contents
are not constrained by the eligibility that was supposed to determine them. A
player who never registered can be stored as a participant, and a participant
earns rating.

**It is also the one finding that a second engine cannot work around**, because
it is not the engine's to fix — it belongs to the storing operation (§10.6).

**Recorded as `BDC-R4`**, and it is the same defect the Match Team Assignments
specification records as `TA-R1`. **This contract does not restate it as new —
it records that the contract's own Final Participation term is currently
unenforced.**

### 13.2 Boundary violation — a second write path to the lineup exists

Direct row-by-row write rules on `match_team_assignments` permit an authorised
actor to bypass the replacement operation entirely.

**In contract terms this breaches both the Business Transition Principle
(§10.3) — a state change reachable by a route other than the operation that
owns it — and the Single Business Path Principle (§10.6).**

It also defeats §7.1: a row-by-row path is not atomic, which is the failure the
replacement operation was introduced to eliminate.

**Recorded as `BDC-R5`**; the same finding as `TA-R3`.

### 13.3 Duplicate responsibilities — none

**No fact BTGE produces is stored twice, and no fact it reads is mirrored into
its output.** Out-of-position is derived from the basis rather than stored;
metrics are computed and discarded; no rating, counter or result field appears
in the lineup.

**The contract is clean on this axis**, and §5.4's refusal of generation
metadata is what keeps it so.

### 13.4 Database coupling — low, with one stale-read gap

**The engine itself is fully decoupled**: it consumes domain types and knows no
table. The coupling lives in the assembling layer, which is where it belongs.

**One gap:** a proposal is computed from the roster as it stood when it was
read. **If a player withdraws or is removed between generation and storing,
nothing detects it**, and the organiser can store a lineup containing someone
who is no longer registered.

**This is not a separate defect — it is `BDC-R4` reached by an innocent
route**, and it is the strongest argument that the validation belongs in the
storing operation rather than in the caller: only the store can check against
the roster as it is at the moment of writing.

Recorded as `BDC-R6`.

### 13.5 Determinism — a device-dependent input

The match date is read in the device's local time (`DD-11`), and age is derived
from it. **Two organisers in different time zones can therefore compute a
different age for a player whose birthday falls on the match date, and
potentially a different lineup** — while the engine is otherwise deterministic
with no seed.

**The practical impact is small** (one region, and only for a birthday landing
exactly on the match date). **The contractual point is not:** the input set is
not purely a function of the database.

**Noted alongside, without asserting a conflict:** the statistics layer uses a
fixed reference zone (`Asia/Muscat`) for exactly the reason that a derived
bucket must not depend on who is asking. The two rules coexist because they
answer different questions, and `DD-11` is approved — **this contract records
the inheritance rather than proposing a change.**

Recorded as `BDC-R7`.

### 13.6 Future extensibility — sound, with one trap

§12 shows the contract admits alternative engines, draft mode, captains, AI
proposers and multiple strategies without a database change.

**The trap is `assignment_basis`** (§12.2): a fourth value silently reduces the
out-of-position count, because that measure is *defined* as exactly
`TRANSITION`. Any new producer that introduces one breaks a measure it may not
know exists.

### 13.7 Summary

| Finding | Verdict |
|---|---|
| Ownership — unconstrained lineup contents | **Open**, `BDC-R4` — breaches §10.5 |
| Boundary — a second write path | **Open**, `BDC-R5` — breaches §10.3 and §10.6 |
| Duplicate responsibilities | **None** |
| Database coupling | **Low**; one stale-read gap, `BDC-R6` |
| Determinism | One device-dependent input, `BDC-R7` |
| Future extensibility | **Sound**; one trap recorded |

**No approved behaviour is redesigned by any of the above.**

## 15. Engineering Rationale

### 15.1 The contract is mostly negative, and that is correct

Two thirds of this document states what BTGE may **not** do. That is not
defensiveness: a component that reads five tables and produces the record every
figure depends on will accrete ownership unless the boundary is written down.
Each prohibition in §6.2 is individually the kind of thing someone would add
for a good reason.

### 15.2 Generation writes nothing, and everything follows from it

If generation stored its own output, the engine would be the author of the
record, `BTGE-MO-3` would be unenforceable, and `KB-017`'s reality/learning
boundary would have nowhere to sit. **The separation of *compute* from *store*
is the load-bearing term in the whole contract.**

### 15.3 One write path admits every future producer

Because generation, adjustment, draft mode, captain picks and any future engine
all hand a lineup to the same operation, a single validation there governs all
of them. **That is why §16.1 is worth closing once rather than per producer**,
and why §12 can promise so much compatibility with so little change.

### 15.4 The one loop is bounded by five rules

BTGE reads its own past output. That is a feedback loop in shape, and
`BTGE-AX-1` … `AX-5` are what keep it from being one in substance: bounded to
priority 5, after everything else is satisfied, as a tie-break only, never a
ranking, never inferred from. **The contract's job is to make that boundary
survive the next engine.**

### 15.5 History records reality, never process

`KB-017` is the sharpest idea in the design, and §5.4, §9.3 and §10.4 are all
applications of it. The record says what played. It does not say who proposed
it, what it scored, or what it replaced — and each of those absences is what
makes the next feature safe to build.
